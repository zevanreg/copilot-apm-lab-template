# Instructor guide and review rubric

## Teaching intent

The application task is deliberately small. The advanced work is designing and
operating a reusable Copilot context supply chain: selection, composition,
versioning, discoverability, reproducibility, distribution, negative testing,
and protected review.

Participants should already know VS Code Agent mode, basic Git, and ordinary
application testing. Do not turn the session into an introductory Copilot demo.

## Before the session

1. Complete [Azure DevOps hosting](azure-devops.md) in the actual training project.
2. Prefer a repository per participant/pair. For shared repositories, establish
   feature branches and a no-merge policy for competing workshop solutions.
3. Rehearse the entire setup from a fresh clone on a learner-equivalent account.
   Include guarded context materialization before any source-package edits;
   copied lock metadata is not APM's local overwrite receipt.
4. Verify custom agent, prompt, and skill discovery in the selected VS Code build.
5. Verify the approved models can use the required local tools under org policy.
6. Verify hosted-agent capacity or prepare an approved Windows pool.
7. Run starter CI and confirm the two hosted artifacts.
8. Preserve a reviewed starter tag.
9. Prepare your own completed reference branch in a separate instructor checkout
   or restricted repository. Do not put a discoverable solution skill or completed
   application implementation in the learner's starter workspace.
10. Verify the complete reference branch in graduation mode.

Local automation cannot verify Azure permissions or VS Code discovery on behalf
of a real learner. Those are mandatory rehearsal items.

## Expected untouched state

| Check | Expected |
|---|---|
| Type check and build | Pass. |
| Baseline application tests | 10 pass. |
| Acceptance application tests | 1 pass, 6 fail for the seeded behavior. |
| Helper tests | 3 pass. |
| Root and second consumer audit | Pass. |
| Cold replay and APM workflow tests | 5 pass. |
| Package authoring checkpoint | Fails until the learner authors version 1.1.0. |
| Graduation | Fails until all learner requirements are completed. |
| Pipeline default | Starter mode, explicit acceptance-required false. |

The negative APM cases are inside successful workflow tests: the tests assert that
the underlying CLI returns nonzero for the intended condition. They do not skip
or ignore a failed command.

## Suggested facilitation schedule

| Segment | Time | Facilitation focus |
|---|---:|---|
| Setup before timer | 20-30 min | Authentication, tools, discovery, starter health. |
| Lab 1 | 15 min | Three separate questions: guidance, integrity, behavior. |
| Lab 2 | 25 min | Bounded implementation with real test evidence. |
| Lab 3 | 20 min | Transitive composition and portable frozen replay. |
| Lab 4 | 35 min | Progressive loading, source ownership, real distribution. |
| Lab 5 | 30 min | Negative-case specificity and honest policy boundaries. |
| Lab 6 | 25 min | Hosted graduation mode and required PR validation. |

For a shorter session, complete setup beforehand and make the optional remote
package distribution an instructor demo. Do not remove the negative cases or
replace them with slides: they are central to advanced understanding.

## Answer-key guidance without a copied implementation

### Application behavior

A correct implementation validates and normalizes before delivery. It checks
whether the normalized event identifier already exists. An existing event with
matching order and quantity returns the original dispatch as a replay; an existing
identifier with different business content returns a conflict. Only a new valid
identifier creates a dispatch.

The check/create decision must not introduce an asynchronous gap in this
single-process exercise. A raw `JSON.stringify` comparison is not sufficient
because property order and whitespace normalization are part of the task.

Do not require a particular algorithm, map, function length, or model response.
Use the observable contract and tests. An in-memory implementation must not claim
distributed coordination, persistence, authentication, or signature verification.

### Package authoring

The expected change is:

- Webhook package version 1.1.0.
- A linked release-evidence reference with required-evidence, rollback, and limits
  sections.
- One narrowly scoped package-Markdown instruction.
- Both consumers regenerated by APM, with matching source hashes and installed
  resources.
- A curated standalone release, not an unsupported attempt to pack local
  development dependencies.

The heading and file checks are only structural gates. Read the actual guidance.
Reject evidence instructions that invent test success or contain unsafe rollback
advice.

### Governance

Two different failures must be explained:

- A deployed instruction is modified without changing authored source or the lock.
  Audit must name the drift/integrity problem.
- A candidate declares a harmless manifest command. Explicit local policy audit
  must fail `scripts-policy` without executing the command.

The automated third negative case changes local package source and requires frozen
installation to reject it. Learners should distinguish all three.

Do not let participants describe a local policy file as an automatically enforced
organization policy, or an audit as a runtime sandbox.

## Review rubric

Score each area 0-2: 0 missing/incorrect, 1 partially demonstrated, 2 demonstrated
with reviewable evidence.

| Area | Full-credit evidence |
|---|---|
| Behavioral diagnosis | Named failing acceptance assertions and accurate mutation/status reasoning. |
| Context consumption | Actual installed paths and observed Copilot skill/prompt/agent use. |
| Application completion | 10 baseline and all 7 acceptance tests pass, no weakened or skipped assertions. |
| Dependency understanding | Correct direct/transitive graph and explanation of source/lock/cache ownership. |
| Reproducibility | Frozen locks unchanged; cold replay and reuse pass. |
| Authoring quality | Scoped, discoverable, meaningful version 1.1.0 guidance with usable references. |
| Distribution | Real ZIP installed and audited in an empty consumer; artifact hash recorded. |
| Negative cases | Drift and scripts-policy failures for the correct reason, then clean repairs. |
| Azure integration | Actual graduation-mode hosted build and required PR build-validation policy. |
| Trust boundaries | Accurate limits; no fabricated evidence, embedded credentials, or sandbox claims. |

Suggested completion threshold: 16/20, with no zero in application completion,
negative cases, Azure integration, or trust boundaries. This is a facilitation
rubric, not an automated product certification.

## Common interventions

- **Copilot rewrites everything:** narrow scope to application source and point at
  the existing contract and tests.
- **Someone edits deployed guidance:** ask which file is authoritative; let Lab 5
  make the failure visible rather than silently repairing it.
- **A green build is called graduation:** inspect the summary mode and whether the
  acceptance step actually ran.
- **A negative test fails for authentication:** do not accept it as policy evidence.
  Separate environment failure from the named expected check.
- **A copied folder is called isolated:** explain APM project scope versus Git,
  VS Code discovery, and process security.
- **An unsupported bundle command is suggested:** use the explicitly tested format
  and curated release flow. Do not patch locks or disable integrity checks.
- **An agent claims tests passed without output:** ask for independently runnable
  commands and actual logs.

## Recovery without losing learner work

Use a new chat for stale customization discovery. Review a specific diff for an
unexpected edit. Restore only the controlled drift marker through the helper.
Regenerate approved source changes intentionally through APM.

If a learner needs to start again, have them preserve their branch and create a
new checkout from the starter tag. Do not run destructive resets over their work.
Do not recursively delete broad folders or terminate processes by name.

## Final acceptance by the facilitator

Inspect the final commit, evidence, PR check, and downloaded CI summary. Confirm
the artifact says graduation and that it corresponds to the final PR commit.
Open the released ZIP or install it in an approved scratch consumer if needed.

Record environment or Azure-permission blockers honestly. A correct local lab
without a hosted build is **locally complete, Azure validation pending**, not
fully graduated.
